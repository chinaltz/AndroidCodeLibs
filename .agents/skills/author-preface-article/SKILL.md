# 作者手写开篇 · 定稿规则

技趣星球部分文章采用 **双段作者结构**：上方是作者手写，下方是 AI 扩写。Agent 处理时必须遵守本 Skill。

## 固定版式（必须按此顺序）

```markdown
自己写的：

[作者原文，逐字保留，段间空行保持作者原样]

---

下面是AI 写的

# 文章标题

[以下为 AI 可优化正文…]
```

| 区块 | 是否可改 | 说明 |
|------|----------|------|
| `自己写的：` | ❌ 标签不可删 | 固定写法，含中文冒号 |
| 手写正文 | ❌ 逐字保留 | 不润色、不合并段落、不改标点 |
| `---` | ✅ 必须保留 | Markdown 分割线，导出 HTML 为虚线 |
| `下面是AI 写的` | ❌ 逐字保留 | **固定文案**，不是「下面是 AI 写的」或「AI 总结」 |
| `# 标题` 及以下 | ✅ 可优化 | improve-style、结构、配图、去重 |

**参考定稿**：`content/posts/12-word-planet-product-prototype/index.md`

## 铁律（不可违反）

1. **「自己写的：」块必须在全文最上方**，其后才是 `---`、`下面是AI 写的`、标题。
2. **手写原文逐字保留**：不删句、不改词、不润色、不把口语改成「博客腔」。
3. **`---` 与 `下面是AI 写的` 两行必须同时存在**，终审时不得删掉。
4. **AI 段不得重复手写块**：动机、Token 限制、先原型后编码等，只在上方出现一次。
5. **禁止把手写块当草稿删除**；禁止只留 AI 段。
6. **生成 HTML / DOCX / 发布前**：核对三段结构是否完整。

## Agent 可优化的范围

仅 **`下面是AI 写的` 之下**（从 `# 标题` 起）：

- 语气润色、结构合并、小标题/表格
- 补提示词、流程图、配图引用
- 去掉微信引流、旧式 `*** … ***` 编辑备注
- 统一中文引号「」、难度星级、文末小结

**不可优化**：`自己写的：` 至 `---` 之间的全部内容，以及 `下面是AI 写的` 这一行本身。

## 禁止事项

| 禁止 | 说明 |
|------|------|
| 删掉「自己写的：」或手写正文 | 常见误操作：终审当草稿删 |
| 删掉 `---` 或 `下面是AI 写的` | 破坏双作者结构 |
| 改成「下面是 AI 写的」「AI 根据会话总结」等变体 | 固定文案见上表 |
| AI 段重复「工作太忙、Token 有限…」 | 与手写块去重 |
| 润色后替换文首手写 | 只能改 AI 段 |

## 与 review-post 联动

审查时额外检查：

- [ ] 文首是否为 `自己写的：` → 手写正文 → `---` → `下面是AI 写的` → 标题
- [ ] 手写块与用户提供版本逐字一致
- [ ] `下面是AI 写的` 是否存在且未被改写
- [ ] AI 段与手写块无大段重复

## 完整示例（结构）

```markdown
自己写的：

工作太忙了，每天剩下 寥寥无几的时间，有时候还得花时间带孩子听写，如果加班有时候连日常听写都会落下，经常无法日常带娃进行字词听写。

既然音标的做了，那把听写也加上吧。

AI做产品的能力一般，如果你有完整的设计文档和需求文档他去编码还行。给他 一个实用场景让他发挥完善功能。做的很差，经常无法准确的达到你的要求。

而且上下文和 Token都有限，有时候有些工作就要从头开始。

目前我的方案是  先不让他进行编码阶段，就进行 原型 需求的review，和需求文档 和设计文档的输出。人工审核后再进入编码。按照文档进行编码是AI的强项

他不需要发散思维，只需要在边界内实现
```

## 发布

三段结构均参与 HTML/DOCX 导出：

```bash
npm run build:html -- content/posts/<slug>
npm run convert -- content/posts/<slug>
```

HTML 中：`---` → 虚线 `<hr>`；`下面是AI 写的` → 普通段落，位于虚线与 `<h1>` 之间。
